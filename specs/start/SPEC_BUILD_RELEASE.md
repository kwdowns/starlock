## 2. Dependency Strategy

### 2.1 tetra3rs (plate solver)

The solver is `tetra3rs` — a Rust/pyo3 port of ESA's tetra3 — installed from a prebuilt
wheel (no vendoring, no Rust toolchain). It ships `win_amd64` + `manylinux_2_28`
(x86_64/aarch64) wheels for cp312/cp313, so `uv sync` downloads the wheel; `cargo`/`rustc`
never run.

```toml
dependencies = ["tetra3rs==0.7.1", ...]
```

### 2.2 Python dependency locking

Uses `pyproject.toml` (hatchling build backend) with `uv` for dependency locking (`uv.lock`).

Dependencies: pywebview, Pillow, numpy, tetra3rs, playsound3, aiohttp, pyerfa (>=2.0.0, for LX200 J2000↔JNow precession). The React front-end (under `web/`) is built separately with Vite (Node deps from `web/package.json`) and bundled into the Nuitka output as a data dir.
Dev dependencies: nuitka (>=4.0.2), pytest

## 3. macOS Build

### 3.1 Build the camera subprocess (Swift)

Uses Swift Package Manager (SwiftPM):

```bash
scripts/build_camera_mac.sh
# Runs: swift build -c release
# Produces: camera/mac/.build/release/camera_server
```

Backend uses:
- AVFoundation (capture)
- IOKit (UVC controls via USB control requests)

### 3.2 Build the Python app as a binary

Uses Nuitka in `--standalone` mode (produces a `.dist/` directory):

```bash
scripts/build_mac.sh
```

Key Nuitka flags:
- `--standalone` (NOT `--onefile` — `.dist/` directory approach)
- `--output-filename=Starlock` (binary name; macOS/Linux) or `Starlock.exe`
  (Windows). The binary name matches the app/bundle name on purpose:
  macOS TCC reads it for the camera permission prompt, Windows Defender
  Firewall reads it (alongside the version-info `ProductName`) for the
  network prompt, and on Linux it keeps `ps`/`top` output legible.
- `--include-package=erfa` (bundles the pyerfa C extension used by the LX200
  J2000↔JNow precession helpers)
- `--include-package=` for `numpy`, `PIL`, `playsound3`, `tetra3rs`, `webview` (packs the compiled `tetra3rs` extension)
- `--include-data-dir=web/dist=web_dist` (or `data/web_dist` on Linux/Windows) bundles the React build
- Other data files (database, sounds, fonts, marketing) are copied manually post-build

## 4. macOS Packaging (.app and .dmg)

Final distributable: DMG containing `Starlock.app`

Expected `.app` layout:

```
Starlock.app/
  Contents/
    MacOS/
      Starlock            # Nuitka standalone dist (CFBundleExecutable)
      camera_server      # Swift binary
      ...                # Nuitka support files
    Resources/
      tetra3rs_gaia.bin
      VERSION.json
      sounds/
      web_dist/
      marketing/
    Info.plist
```

The Python app discovers resource paths relative to the executable location
via `evf/paths.py` (walks up to `../Resources` inside the .app).

Info.plist is generated by the build script with proper app metadata.

## 5. Linux Build

### 5.1 Camera server

```bash
make -C camera/linux
# Produces: camera/linux/camera_server
```

### 5.2 Python app

```bash
scripts/build_linux.sh
```

Uses Nuitka `--standalone`. Post-build assembles an AppImage:
- Downloads `appimagetool`
- Creates AppDir with Nuitka dist, camera binary, data files
- Includes `linux/starlock.desktop` for desktop integration
- Produces both `Starlock-linux-{ARCH}.tar.gz` (raw standalone dist) and
  `Starlock-linux-{ARCH}.AppImage` (self-contained single-file distributable)

## 6. Windows Build

### 6.1 Camera server

```bash
camera\windows\build.bat
# Compiles C/DirectShow camera server
```

### 6.2 Python app + installer

```bash
scripts\build_windows.bat
```

Uses Nuitka `--standalone`. Post-build:
- Copies camera binary, data files, marketing assets
- Produces `Starlock-windows-x64.zip` (raw standalone dist, always)
- If Inno Setup is installed (`ISCC.exe` on PATH), also runs
  `scripts/starlock.iss` to build `Starlock-windows-x64-setup.exe`. The
  installer step is skipped silently when Inno Setup is not present.

DPI awareness is handled at runtime (not build-time) via Windows API calls in `main.py`.

## 8. Path Resolution (`evf/paths.py`)

Centralized path resolution handles dev repo, macOS .app bundle, Linux release, and
Windows release:

- `tetra3rs_database_path()` — tetra3rs star catalog (`tetra3rs_gaia.bin`)
- `camera_binary_path()` — platform-specific camera server binary
- `sounds_dir()` — audio files
- `web_dist_dir()` — built React UI (release-only; in dev served by Vite on :5173)
- `title_image()` — in-app branding

Detection heuristics:
- macOS release: `_MAC_RELEASE` — executable inside `.app/Contents/MacOS/`
- Linux release: `_LINUX_RELEASE` — `data/` sibling to executable
- Windows release: `_WINDOWS_RELEASE` — `data/` sibling to executable
- Dev mode: falls back to repo-relative paths

## 10. Dev Mode (Fast Iteration)

Platform-specific dev scripts:

```bash
scripts/run_dev.sh              # macOS
scripts/run_dev_linux.sh        # Linux
scripts/run_dev_windows.bat     # Windows
```

These run the Python app in the normal interpreter, spawning the camera server
and using local data files. Avoids Nuitka while iterating on behavior and UI.

`scripts/run_mock_camera.sh` launches a mock camera server for testing without hardware.

Launch with `--dev` flag for debug features.

## 11. Versioning

### Product versions (all components)

Starlock ships as several components in separate repos: this engine (the
`starlock-headless` Pi package), Starlock Cloud, and the iOS app (Android
later). They share one version scheme:

- **SemVer `MAJOR.MINOR.PATCH`, numbers only.** No `-beta` / `-rc`
  suffixes: iOS's `CFBundleShortVersionString` only takes digits and dots,
  and the Pi and app should show exactly the same string. Staying below
  1.0 says "not finished"; TestFlight is the iOS beta channel. 1.0.0 is the
  first release you sell.
- **`MAJOR.MINOR` is the product release, shared by every component.**
  "Starlock 0.4" means engine 0.4.x, cloud 0.4.x and app 0.4.x. Starting a
  new minor (a feature release) bumps every component to `X.Y.0`, even one
  that didn't change, so users can match them at a glance.
- **`PATCH` is per component.** A cloud hotfix is cloud 0.4.3 while the
  app stays 0.4.1; no empty App Store releases.
- **Compatibility is decided by the API versions, not by matching
  numbers:** the Bonjour TXT `api` and `/api/version` here, the cloud's
  `/v1` path, `protocol_version` for the camera protocol. A breaking API
  change bumps those (and, before 1.0, the minor).
- **Releases are git tags `vX.Y.Z`** in each repo, on the commit whose
  version file says `X.Y.Z`.
- **Build numbers** (iOS `CFBundleVersion`) are a separate, ever-increasing
  counter (the CI run number). TestFlight shows them as "0.4.0 (37)"; the
  App Store shows only "0.4.0".

Where each component keeps its version (the one place to edit):

| Component | File | Shown as |
|---|---|---|
| Engine / Pi package | `data/VERSION.json` `app_version` (and `pyproject.toml`, kept equal by a test) | `/api/version`, Bonjour TXT `version`, `.deb` `X.Y.Z-1` |
| Starlock Cloud | `Directory.Build.props` `<Version>` | `/healthz`, image tag |
| iOS app | `project.yml` `MARKETING_VERSION` | App Store / TestFlight version |

### `data/VERSION.json`

```json
{
  "app_version": "<x.y.z>",
  "protocol_version": 1,
  "solver_db_version": "tetra3rs_gaia_<hash>_mag8"
}
```

`protocol_version` and `solver_db_version` are stable across minor releases;
`app_version` follows the product scheme above and must equal
`pyproject.toml`'s `version` (checked by `tests/test_version.py`).
Logged at startup (INFO).
